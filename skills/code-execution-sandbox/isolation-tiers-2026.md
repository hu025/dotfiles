# Agent Sandbox Isolation — 2026 Decision Guide

## Core Problem

LLM agent generates code at runtime → cannot review before execution. Traditional container isolation fails because shared-kernel CVE compromises all tenants simultaneously.

## Four Isolation Tiers

| Tier | Technology | Boot | Memory | Isolation | Host Kernel |
|------|-----------|------|--------|-----------|------------|
| 0 | exec() / subprocess | 0ms | 0MB | ❌ None | ✅ Full access |
| 1 | Docker/LXC (runc) | ~200ms | ~10MB | Namespaces+cgroups | ✅ Shared |
| 2 | gVisor (runsc) | ~50ms | ~30MB | User-space kernel | ❌ Intercepted |
| 3 | Firecracker microVM | ~125ms | ~5MB | Hardware VM | ❌ Isolated |
| 4 | TEE (SGX/SEV-SNP) | ~1s+ | Limited | Hardware memory encrypt | ❌ Unreachable |

### Tier 1 — Standard Containers
**Isolation**: Shared host kernel. CVE-2024-21626 (runc), CVE-2025-59528 (CVSS 10.0) allow container escape.
**Use**: Trusted code only, single-tenant, prototyping.
**Hermes current**: `execute_code` uses Tier 1 (Docker container).

### Tier 2 — gVisor (User-Space Kernel)
**Isolation**: Sentry process intercepts all syscalls in Go. Guest never reaches host kernel.
**Modes**: Systrap (seccomp, better compat) / KVM (hardware virt, fastest on bare-metal).
**Overhead**: 10–20% per syscall.
**Attack surface**: gVisor codebase ~70% syscall coverage. Compromise = process escape (not host).
**Used by**: Modal, Beam, Northflank.
**Use**: Compute-heavy multi-tenant, Python/ML pipelines.

```bash
# gVisor Docker runtime registration
curl -fsSL https://gvisor.dev | sh

# gVisor sandbox wrapper (network=none, 256MB RAM, 10s timeout)
docker run --rm -i \
  --runtime=runsc \
  --network=none \
  --memory=256m --cpus=0.5 \
  --pids-limit=64 \
  --read-only --tmpfs /tmp:size=16m \
  --cap-drop=ALL --security-opt=no-new-privileges \
  python:3.14-alpine \
  timeout 10 python3 -
```

### Tier 3 — Firecracker MicroVM
**Isolation**: Full Linux guest kernel via KVM. AWS Lambda/Fargate technology.
**Boot**: ~125ms, 5MB overhead, 150 VMs/sec per host.
**Attack surface**: Requires VM escape (not container escape). Orders of magnitude harder.
**Used by**: E2B, Cloudflare Workers Isolates, Vercel, CodeSandbox, Northflank.
**Use**: Untrusted LLM-generated code, multi-tenant production, regulated industries.

```bash
# Firecracker self-hosted (Ji-ho Choi, Aug 2026 verified)
# 1. Install
wget https://github.com/firecracker-microvm/firecracker/releases/...
tar -xzf firecracker-*
sudo install firecracker /usr/local/bin/

# 2. Create rootfs (Ubuntu ext4 from canonical cloud-images)
# 3. Launch with jailer + seccomp
./firecracker --api-sock /tmp/firecracker.sock
```

### Tier 4 — Confidential Computing (TEE)
**Isolation**: Intel SGX/TDX, AMD SEV-SNP. Even hypervisor cannot access VM memory.
**Use**: Financial services, healthcare, defense.
**Trade-off**: Higher overhead, memory limits, complex programming model.
**Platforms**: Azure Confidential Computing, AWS Nitro Enclaves.

## Five Sandbox Controls

1. **Network egress** — default-deny, explicit allowlist
2. **Filesystem** — scoped workspace, read-only base image
3. **Process** — dedicated kernel (Tier 2+) or VM (Tier 3+)
4. **Secrets** — never inject credentials into sandbox
5. **Ephemeral lifecycle** — state does not persist unless explicitly opted in

## Hermes Current State

Hermes `execute_code` tool: Tier 1 (Docker subprocess). **Adequate for trusted code** (generated by Hermes itself). **Not sufficient for untrusted code** (external prompts, web-derived).

**Upgrade path**:
1. Low cost: gVisor wrapper for `execute_code` (Tier 2, ~50ms boot, single host)
2. High security: Firecracker self-hosted (Tier 3, ~125ms boot, full VM isolation)

## Decision Matrix

| Scenario | Recommended |
|----------|-------------|
| Local dev, trusted code | Tier 0 (exec) |
| Prototype, single-tenant | Tier 1 (Docker) — current Hermes |
| Multi-tenant, compute-heavy | Tier 2 (gVisor) |
| Untrusted LLM code, regulated | Tier 3 (Firecracker) |
| Financial/healthcare | Tier 4 (TEE) |

## gVisor vs Firecracker for Hermes

**gVisor** advantages: Sub-second cold start, lower memory overhead, Docker-compatible OCI runtime, no VM management.
**Firecracker** advantages: Strongest isolation (hardware VM boundary), no shared kernel code paths, AWS production proven (trillions of Lambda invocations).

**Recommendation for Hermes self-hosting**: gVisor first (easier operational burden), Firecracker when isolation > performance.
