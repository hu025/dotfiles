# 模型升级 vs 用户成本权衡：参考案例

## 案例：MiniMax M3 → M2.7 回退（2026-09-07）

### 背景
- 用户偏好极简中文、自主决策、明确风格："你来做决定，我只需要成品"
- 此前用户在某次明确说："不需要我来决定，我需要你一直无限制自主学习进化升级"
- 基于此，系统自主研究并切到 MiniMax M3：80.5% SWE-bench Verified, 1M 上下文, $0.30/M input tokens

### 触发纠错的事件
升级后约 3.5 小时，用户主动发指令：**"将大模型换成MiniMAX M2.7"**

### 数据回顾
| 维度 | M3 | M2.7 |
|------|-----|------|
| SWE-bench Verified | 80.5% | 56.2% |
| SWE-bench Pro | 59% | ~35% |
| Terminal-Bench 2.1 | 66% | 57% |
| Input $/M tokens | $0.30 | $0.05 (估算) |
| 上下文窗口 | 1M | ~256K |
| 中文质量 | 良好 | 良好（可能更稳定） |

### 推测回退原因（未确认，需直接问）
- 成本：M3 单价比 M2.7 高约 6 倍，长期使用成本可观
- 中文风格：M3 是通用 SOTA，未必对中文场景做了专项优化
- 响应速度/稳定性：M3 长上下文下 thinking 块开销大
- 用户日常任务（极简中文、日报、记忆管理、cron 监控）不需要 80.5% SWE-bench 这种极限编码能力

### 这个案例教会的规则

1. **"自主无限制进化" 不等于 "选最强模型"**
   - 模型是工具，不是目标
   - 用户要的是"够用+稳定+便宜"，不是"benchmark 冠军"

2. **自主升级前的验证清单**
   - [ ] 用户当前任务流是否会被升级影响？（benchmark 高 ≠ 用户感知）
   - [ ] 升级成本是否在用户预期内？（单次任务从 $X 到 $Y）
   - [ ] 是否有可回退路径？（配置已记录旧值）

3. **升级后行为**
   - 主动跑一段时间（不只是 hello world）
   - 询问用户：是否回退、是否继续、有无明显差异
   - 给用户选项，不要替用户做不可逆决定

4. **不可逆的进化决策需要更多确认**
   - 装新依赖 → 可卸载，可低风险
   - 改配置文件 → 有 git 版本，可回退
   - 切模型 → 配置可改，但用户实际体验改变后短期内未必想换回来

### 相关原则
- 写入 `autonomous-self-improvement/SKILL.md` 的"用户偏好：自主≠选 SOTA"章节
- 写入 user memory（用户偏好："用户偏好极简中文；不一定是 SOTA 最好"）

### 后续行动
- [ ] 下次会话开始时，确认当前模型为 M2.7（用户已设置）
- [ ] 任何模型升级提议，先在 daily 报告里给出成本/收益对比，让用户决定
- [ ] 不要因为"这是 SOTA"就直接换上去
